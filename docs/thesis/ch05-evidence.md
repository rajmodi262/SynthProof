## 5.3 Noise sampling (~300 words)

| Claim | Evidence |
|---|---|
| Discrete Gaussian by rejection sampling, CKS'20 §5.2 Alg. 1 | `accounting/noise.py::_discrete_gaussian_single` |
| Discrete Laplace as a two-sided geometric | Ghosh, Roughgarden & Sundararajan (2012) |
| Why discrete at all | Mironov (2012): inverse-CDF float sampling leaks through low-order bits. Rounding a continuous Gaussian does **not** give a discrete one |
| The sampler is validated, not asserted | χ² goodness-of-fit against the exact PMF, `tests/test_accounting.py:99` — tails folded so no expected bin is too small |

**The defect to report, and it is the best paragraph in this section.** A previous version returned a deterministic zero vector for σ < 0.3. The accountant still charged a finite ε. So the release paid budget *and* leaked deterministically — worse than not paying at all, which is why it became standing rule 3. The fix is a refusal to special-case: `accounting/noise.py:133` now carries a comment explaining that the rejection sampler is valid for every σ > 0 and concentrates on 0 for small σ *by sampling rather than by fiat*.

[WRITE: ~300 words. Lead with why discrete, then the validation, then the defect. The defect is the point: a one-line shortcut voided the guarantee silently and no test would have caught it without a distributional check.]

## 5.4 Calibration implementation (~250 words)

| Claim | Evidence |
|---|---|
| Bracket-and-bisect inversion of the composition theorem | `accounting/calibration.py::calibrate_noise_scale` |
| Budget split routed through one implementation | `calibration.py:160` calls `Allocator.allocate_weighted` |
| Never overspends | proved/target ≤ 1 across the whole grid — see `ch07-tables.md` §7.1 |
| CI-gated | across 24 configurations |

**The motivating failure:** before calibration, `noise_scale = sqrt(num_columns) / target_eps` was set by hand and a target of **8.0 composed to 70.49** (audit finding F2). Every step was individually sound; the number the operator typed simply did not mean what they thought.

[WRITE: ~250 words. The general claim worth making: a system can satisfy the DP definition while its interface deceives its operator. Song et al. (CSCW 2024) found practitioners do not verify DP guarantees, which is what makes that class of failure durable. Cross-reference Ch.4 §4.4 rather than repeating the result.]

## 5.5 Ledger implementation (~250 words)

| Claim | Evidence |
|---|---|
| Canonical bytes: sorted keys, fixed-precision floats | `ledger/types.py::canonical_bytes` — `%.8f` for ε and sensitivity, `%.8e` for δ |
| Why fixed precision | float repr varies; without it a signature is not reproducible and verification fails on a byte-identical record |
| Chain + signature | SHA-256 over canonical bytes, Ed25519 over the payload |
| Attacks run against **live SQLite**, not the API | `tests/test_ledger_adversarial.py` |

**Chaining alone is not enough, and this is the finding.** A hash chain detects modification, insertion and reordering but **not truncation** — a shortened chain is internally consistent. Deleting the last two entries left `verify()` returning `True`, so an operator could remove exactly the entries recording a budget overspend. A signed `ledger_head` committing to `(entry_count, tip_hash)` closes it: **9 distinct attacks stopped, up from 8**, across 14 tests.

[WRITE: ~250 words. Do not call the ledger 'append-only' — nothing prevents an append; what is detectable is that one happened. State plainly that it does not stop an adversary holding the signing key, and that one shared API key means the `actor` field cannot identify who spent the budget.]
